# Per-change UI review report

One HTML page the owner opens in the browser and reviews change by change. Only approved changes are applied; the page tracks what happened to each. Start from `template.py` in this folder.

## Inputs and output

- Input: screenshots, or a description of a UI area. Read the real numbers and labels off them.
- Output: `index.html` in `docs/scratchpad/<topic>/`, generated by `build.py` beside it (nothing is hand-edited in the HTML). Self-contained: inline CSS, no scripts needed. Fonts links are fine, but the page must read without them.
- Dark theme only, unless the owner asks. Say so in the intro, with other unchecked things (a narrow width).
- Say in the intro that the mocks are your reproductions, not the live page.

## Page layout, top to bottom

1. Title and a short intro: what the screenshots were, that red dashed outlines mark what changes, that these are mocks.
2. **Summary table**: number, change, what it does, size (small or medium), space, status. One row per change.
3. **One numbered section per change** (below).
4. Closing sections: **What is left**, **What I would keep** (parts that say something the numbers cannot), **My pick**, **Open questions**. Keep them current when a change is applied, replaced or dropped; "What is left" shows the current state next to the state with the remaining pick applied.

## A section

Heading: number, title, size tag, status tag. Then, as a label/value grid:

- **What the screenshots show**: the facts, with the real numbers.
- **Why it costs attention**: what the reader has to do because of it.
- **Change**: the proposal, in one or two sentences.
- **Space**: rows or pixels added or saved ("none" if none).

Then **Before** (mock, caption) and **After** (mock, caption). Each caption is one line saying what the red marks cover ("Red: the label.").

## Mocks

- Small HTML/CSS reproductions of the real UI, built from one renderer function that takes an options dict and a set of marks. Same renderer for Before and After; the options differ.
- Real numbers and names from the screenshots, not placeholders.
- The changed parts carry `.hl{outline:2px dashed red;outline-offset:-2px}` in both Before and After. Use `outline`, never `border`, so the layout does not shift between the two.
- Give every markable part a key; a change's marks are a set of keys. Mark the part that changes in Before, and where it ends up in After.
- Slice the mock to what the change touches (`table='head'`, `'tail'`) so the reader looks at the right area; show the whole block only when position matters.
- **Current state.** Keep a `CURRENT` options dict that matches the prototypes as they are now. Pending changes build their Before from `CURRENT`. Applied sections keep the historical Before/After they were reviewed with. When a change is applied, update `CURRENT` (and every later pending mock) to include it.

## Status

A `STATUS` dict keyed by change number; absent means pending.

- **pending**: normal section, amber "Pending your review" tag.
- **applied**: the section becomes a greyed, collapsed `<details>`, the summary row is struck through, a green tag reads "Applied to <targets>".
- **replaced**: same collapse, tag "Replaced by change N" (another change made it moot).
- **dropped**: same collapse, tag "Dropped" (the owner rejected it, or it lost its point).

Set the status, rebuild, reopen. Do not delete settled sections; the history is the point.

## Workflow

1. Build the report from the screenshots. Do not apply anything yet.
2. The owner reviews each change. Apply only the ones they approve, to every target prototype, one at a time.
3. After each applied change: quick-check the targets (build plus a look at the changed area). Run the long walks only when layout changed, or after a batch.
4. Update `STATUS`, `CURRENT`, the closing sections; rebuild.
5. Open the page with `MSYS_NO_PATHCONV=1 cmd.exe /c start "" "file:///C:/.../index.html"` from Git Bash (plain `cmd.exe /c start ...` in Command Prompt), run **alone**, nothing chained. If the project says the owner opens it, rebuild and say so instead.
6. When asked for a recommendation, be honest: if one change makes another moot, say so and mark the second replaced or dropped. Do not pad the pick.
7. New ideas from the owner become new numbered changes, pending until approved. Never renumber old ones.

## Style

- Plain and short: a few words per cell, details in the section text. Neutral wording, no advice dressed up as fact.
- Mark any guess as a guess in the section text.
- Keep the project's own names out of this skill; they belong in the report.

## Checklist

- [ ] Every number in a mock comes from a screenshot.
- [ ] Before and After both carry red dashed outlines (`outline`), one caption each.
- [ ] Pending Befores start from `CURRENT`; applied sections keep their history.
- [ ] Summary table row for every section, with size, space and status.
- [ ] Settled sections collapsed and greyed; row struck through; tag names the targets or the replacing change.
- [ ] Closing sections match the statuses.
- [ ] Nothing applied that the owner did not approve.
- [ ] Opened with the lone start command (or left for the owner).
