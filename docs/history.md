# History of corrections

A log of claims and results that turned out to be wrong, what replaced them, and how the mistake was found. Its purpose is to stop the same mistakes from coming back. Add an entry whenever a published number, a doc statement or a result of the tool has to be retracted.

Each entry has four parts: **when** (`YYYY-MM-DD`, or `YYYY-MM` where only the month was kept; "not recorded" where no date was kept), what was claimed or done, what is true, and how it was found. "What is true" carries the same verified / inferred / second-hand labels as the page it points to ([STYLE.md](diagrams/STYLE.md#status-words)).

Related pages: [validation.md](mechanics/validation.md) (current evidence), [math.md](mechanics/math.md), [optimizer.md](engineering/optimizer.md), [data-pipeline.md](engineering/data-pipeline.md).

## Lessons

Most entries below come from one of these patterns:

- **An inference stated as a fact.** Say what the data shows, and label the explanation as inferred ("unused", not "placeholder").
- **A rounded or remembered number instead of a re-run.** Re-run the code before quoting a figure, and keep one decimal for percentages; 99.5% is not 100%.
- **A result checked only against the code that produced it.** Prefer an independent reference: game data, the Wiki, exhaustive search.
- **Job-specific thinking in a job-agnostic tool.** The owner plays Sage, but the tool serves all 23 combat jobs.

## Results of the tool

| When | What was reported | What is true | How it was found |
| --- | --- | --- | --- |
| Not recorded | The optimizer returns the best loadout unless the search is truncated. | Dominance pruning removed an item when any single better item existed (bug F1), so the second-best ring could be dropped: **360 of 9,800 runs (3.7%)** on real gear were below the optimum. Now an item is dropped only if the items beating it can fill every slot of its type, and pruning is off when a speed maximum is set ([optimizer.md, section 4](engineering/optimizer.md#4-fewer-candidates-dominance-pruning)). | Engineering audit (real-gear probe and random pools against exhaustive search). |
| Not recorded | The lexicographic score with fixed weights $10^8, 10^4, 1$ ranks target, then tiebreak 1, then tiebreak 2. | Only while each tiebreak total stays below 10,000 (bug F3); above that, a tiebreak could outrank the target. Weights are now derived from the pool, and a score that could exceed $2^{53}-1$ raises an error ([optimizer.md, section 3](engineering/optimizer.md#3-turning-the-lexicographic-order-into-one-number)). | Engineering audit. |
| 2026-10-17 | Tier ranking with a Target GCD on all 23 jobs (17,648 cases): median 0.30 s and 95th percentile 0.97 s in exactly mode, 0.21 s and 0.61 s in or faster mode, 2 to 4 times faster than before; given as the merged code's times because the prototype gives the same sets. | Those are the times of Perplexity's prototype. The sets are the same (**verified** on 5,028 cases), but the merged code is slower: in exactly mode median 0.47 s against the prototype's 0.32 s, 95th percentile 1.50 s against 1.08 s (0.69 s and 5.92 s before). Most of the gap is the prototype's meld version cache, kept across runs (**verified** 2026-10-18; tier-ranking.md section 8). The merged code's times on every job are now the 2026-10-18 sweep ([tier-ranking.md, section 8](engineering/tier-ranking.md#8-performance)). | Checking the section against the three-way timing file of 2026-10-17 (the code before, the prototype and the merged code on the same 5,028 cases). |
